## 4. 软件架构（细节见 CODING_STANDARDS §1.2）

| # | 线程 | 名字 | 优先级 | 栈(B) | 周期/触发 | 调度 |
|---|---|---|---|---|---|---|
| 1 | PID+Motor | `pidMotor` | 40 | 1024 | 10 ms | `osDelayUntil` |
| 2 | IMU | `imuAcq` | 37 | 1024 | 10 ms | 计数信号量(TIM6) |
| 3 | Pose | `pose` | 36 | 768 | 10 ms | `osDelayUntil` |
| 4 | LiDAR | `lidarProc` | 34 | 1536 | ~22 ms/块 | `Q_Lidar`(100ms 守卫) |
| 5 | PathGen | `pathGen` | 30 | 1024 | 命令到达 | `Q_Cmd` |
| 6 | BT RX | `btRx` | 28 | 768 | 字节到达 | 计数信号量 |
| 7 | BT TX | `btTx` | 22 | 1024 | 50 ms | `osDelayUntil` |
| 8 | OLED | `oled` | 20 | 2048 | 50 ms | `osDelayUntil` |

- 队列：`Q_Lidar` 8×12B（满则丢）、`Q_Cmd` 4×8B（满则覆盖最旧）、`Q_Path` 16×8B（生产方阻塞 50 ms）
- **没有 Q_Enc**（TIM1/TIM8 硬件 QEP）、**没有 Q_Set**（PID 与电机合并成 1 个任务）
- STOP/NEW_PATH 用**事件标志** `evt_nav`
- 数据流：`BT → Q_Cmd → PathGen → Q_Path → PID+Motor → TIM2/TIM4 → 电机`
  　　　　`MPU6500 → imu.c(陀螺积分) → pose.c → path.c(航向误差→差速)`

**陀螺在控制环里的位置**（常被问）：`imu.c:249` 积分航向 → `pose.c:118` 写进位姿
→ `path.c:191` 算航向误差 → `path.c:224/225` 折成左右轮差速。陀螺管"直不直"，不管"走多快"。

## 6. 五个已修的坑（**重写必复现**）

| # | 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| A | **任务栈溢出 → 整车假死** | 打印 7 个横幅后全停，但 TIM7 还在跳 | 溢出钩子设 **BASEPRI(0x50)**，屏蔽 ≥5 中断却屏蔽不掉优先级 0 的 TIM7 | IMU 栈 512→1024、OLED 1024→2048 |
| B | **`osEventFlagsWait` 返回值当标志位** | `G` 生成路点但车不动、CCR=0 | 无事件时返回 `osErrorResource=-3=0xFFFFFFFD`，`&0x01=1` → 每周期误判 STOP | 先判 `(flags & 0x80000000)` |
| C | **左右轮映射反了** | `f` 正转右轮倒转 | 电机在 PB6/PB7 上但装的是右轮 | `board_pins.h` §3 两组对调 |
| D | **PID 积分被限死** | 只跑到目标速度 28% | `120 × 0.15` = 2% 输出 | kp 3→5、ki 0.15→0.5、限幅 120→4000、PWM 上限 325→840 |
| E | **测试脚本晚到的 STOP** | `G` 后队列为空 | 上一条 `S` 在关串口后才送达 | 发完命令等送达再关串口 |

**排查心法**：
- "TIM7 在跳但任务全不动" → 查 **BASEPRI** 和栈溢出钩子，别怀疑调度器
- CMSIS-RTOS2 返回值 → 先按 `osOK` 语义判断，再做位运算
- 车不动 → 先读 **CCR** 确认固件在输出 → 再读**编码器** → 最后才怀疑硬件

### 8.0.1 关于右轮 0.5~0.64× / 4~5.5× 的判断（**已被实测推翻，见 §8.0.2**）

永磁直流电机在**同一占空比**下，正反转的转速比不可能到 4~5.5 倍 —— 那个数量级只能是**计数**错了，
不是**转速**错了。而"一个方向只有一半、另一个方向反而多出几倍"，最像**编码器某一路输入在离边**
（悬空脚被噪声来回触发，或接触不良只在某个方向导通）：走一路只算 1/2，回一路被噪声灌成 4 倍。
所以顺序应该是：

1. 先让 `-Test symmetry` 把四组计数打出来，**人眼看两轮转速是否相近**（脚本会提示记 yes/no）；
2. 两轮看起来一样快、计数却差几倍 → **编码器接线**，去查右编码器（PA8/PA9）的 A/B 两根线：
   杜邦头是否松、是否有串电阻、地线是否共地；
3. **不要**先上 `MOTOR_RIGHT_SCALE` 增益补偿 —— 补偿的是电机，治不了计数。
   顺带记着：`Core/Src/motor.c:33-34` **已经有** `MOTOR_LEFT_SCALE 1.08f` / `MOTOR_RIGHT_SCALE 1.0f`
   这个旋钮，但它乘的是**目标 rpm**（`motor_set_target_rpm`），而 PID 的反馈又来自编码器；
   编码器计数错的时候调它只是把错误反馈放大，不解决任何问题。

### 8.0.2 2026-11-18 20:20–21:10 上板实测（**结论都在这里，别再重复查**）

上电 3.25 V，1 Hz 行正常，IMU 100/s，CNT 全 0。以下全部是当晚实测。

**① 右轮"不等速"的真正根因：编码器输入噪声，不是接线、不是电机、不是增益**

用 SWD 直接驱动 H 桥（绕过固件），同一占空比下反复测 `e` 的计数差：

| 场景（2 s） | 修滤波前 dL / dR | 修滤波后 dL / dR |
|---|---|---|
| 右通道单独 | 0 / +2625 | 0 / +3444 |
| 左通道单独 | +13559 / 0 | +4045 / 0（同窗口） |
| 两轮同时正转 | +13166 / **−11697** | +4045 / **+3518** |
| 两轮同时反转 | — | −3421 / −3678 |

右轮自己的 PWM 在"单独"和"同时"两行里**完全一样**，抖动却从 +2625 变成 −11697 —— 方向不可能自己翻，
所以那些计数根本不是轮子产生的。`encoder.c` 的 QEP 输入滤波原来照抄 lessonProgram 的 `ICxF=0011`
（fDTs/2、N=8 ≈ **190 ns**），对碳刷电机来说等于没有。改成 `1111`（fDTs/32、N=8 ≈ **3 µs**）后，
四个方向的符号和幅值全部对上。**固件级复测：R/L 从 1.80 / 4.74 变成 1.03 / 1.14，rev/fwd 0.95 / 1.06。**

> 答辩口径：不是"调了滤波参数"，是"用受控实验证明计数是假的，再让滤波器拒掉它"。
> 谁再提 `MOTOR_RIGHT_SCALE` 补偿，把这个表给他看。

**② 电池/死区：20–30% 是死区，40% 起正常**

用 SWD 写 `CCR` 扫 20/30/40/60/80/100%，两轮都在 **20% 和 30% 完全不转**，40% 开始 ~230 rpm。
所以 `BENCH_DUTY_PCT` 从 **20 改成 40**（`app_rtos.c`），否则 `f/b/l/r` 这四个键在当前电池状态下按下去毫无反应。
**电池仍建议充电**：HANDOVER 12.4 记的"满电 20% → 83 rpm"现在复现不出来。

**③ 陀螺符号正确**：整车逆时针手转 90°，`eh` 89.6° → 172.3°（+82.7°，含手动误差）。转向收敛逻辑可用。

**④ 空中导航（车未落地，位姿系自洽）**：(0, 1400) → 实测 (3, 1390)，**10 mm / 0.7%**，12.1 s（理想 11.7 s）。
这只能证明"蓝牙→路径→PID→编码器"这条链闭合，**不能当成物理精度**，报告里要标"空中"。

**⑤ `PATH: g/r` 是开机累计值，不是本趟进度**

`path.c` 的 `stats_add()` 只加不减，`c` 也不清。空中跑过几趟后 `g=51 r=19` 仍然停在了目标点。
`nav_run` 原来拿 `r>=g` 判到达，结果 1.4 m 的路 1.2 s 就"完成"、真正跑完的反被判超时。
现在判据是 **`QP==0` + 位姿距目标 < max(120 mm, 10%) + 连续两次确认**，并且 `g` 的基线必须在发命令**之前**取。

**⑥ 角色 5 证据已补齐：`i` 键，mutex vs 二值信号量**

```
[demo] mutex    : high waited 61.62ms, holder prio 13 while high waited, 11 after release
[demo] semaphore: high waited 63.67ms, holder prio 11 while high waited, 11 after release
[demo] result: inheritance confirmed (holder 11->13 only with osMutexPrioInherit)
```

注意一个容易讲错的事实：**FreeRTOS 的 mutex 天生带优先级继承**（`xSemaphoreCreateMutex()` 没有"不带继承"的版本），
所以对照物只能是二值信号量 —— 这也正是 CODING_STANDARDS 2.4 规定 I2C 必须用 mutex 的理由。
演示任务优先级 11/13，**低于**最低的真实任务（OLED=20），只在空闲时跑，不扰动控制环。

## 11. 调试技巧（上一轮靠这些才定位到问题）

```powershell
# 1) 取静态变量地址（不需要目标板在线）
arm-none-eabi-gdb -batch -ex "p/x &'motor.c'::s_motor" Debug\CodingDay_F446RE.elf

# 2) 读运行中的内存（mode=hotplug 不复位；mode=UR 会复位！）
STM32_Programmer_CLI -c port=SWD mode=hotplug -r32 0x20002300 32

# 3) 直接写寄存器（绕过固件测硬件；写完记得写回 0）
STM32_Programmer_CLI -c port=SWD mode=hotplug -w32 0x40000034 0x348
```

**重要陷阱**：
- **插上 USB 会复位目标板**（ST-Link 拉 NRST）→ 无线跑完再插 USB 取数据会**丢位姿**
- 判断 MCU 是否真在输出：读 `TIMx->CR1`(CEN) / `CCER`(CCxE) / `CCR` / `CNT` 和 `GPIOx->MODER/AFR`
- `Debug/Core/Src/subdir.mk` 和 `Debug/objects.list` 是 CubeIDE 生成的（`Debug/` 已 gitignore）。
  **新增 .c 后必须同步，否则"编译出 .o 但没链进去"**（text 一点不涨）。IDE 里刷新一次会自动重生成。

## 12. 铁律摘要（完整版见 CODING_STANDARDS.md）

1. PA13/PA14（SWD）永不复用；绝不写 Option Bytes、绝不启用 RDP
2. 任务里禁止任何阻塞（`HAL_Delay`、无超时 I2C、忙等）
3. 每个资源一个所有者；跨任务数据只走队列/信号量/互斥量
4. ISR 只做通知（<5 µs）；调用 RTOS API 的中断优先级必须 ≥5
5. **TIM7 优先级必须为 0，开机 DWT 时基校准不许删**
6. 每个 I2C 事务必须有界（≤10 ms，重试 ≤2 次，连续 3 次失败要恢复）
7. 1 Hz 状态行所有字段必须是真实测量值，不是常量
8. `course_materials/` 和课程 PPT/PDF **禁止提交**
