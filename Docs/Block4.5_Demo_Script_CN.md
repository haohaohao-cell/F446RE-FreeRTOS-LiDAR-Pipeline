# Block 4.5 — 现场演示脚本

目标时长：**演示 5 分钟 + 提问**。
下面所有操作一条命令即可复现，没有任何预录或摆拍。

---

## 0. 演示前 5 分钟

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | 小车**架空**、轮子离地，再打开主电源 | 固件初始化时会把 PB6/PB7 拉低，但不要赌 |
| 2 | 插上 ST-Link 的 USB（同时提供 SWD **和** COM8） | `COM8` 是 ST-Link 虚拟串口，也就是 USART2 |
| 3 | 确认雷达在转、接在 USART3（PC10/PC11） | 不转 = 没有块 = 演示直接死 |
| 4 | 在 **COM8、115200 8N1** 打开终端（PuTTY / Tera Term / CubeIDE 控制台） | 这就是你的"证据屏" |
| 5 | 运行 `tools\flash_and_monitor.cmd -Probe` | 应该看到 `Target OK (voltage 3.2x V)`、`Device name : STM32F446xx` |
| 6 | 先跑一次 `tools\flash_and_monitor.cmd -Seconds 20` | TA 走过来之前先确认端到端正常 |
| 7 | 把最后一次采集的日志窗口留着 | 硬件中途挂掉时的兜底证据 |

**判断流水线是否活着的单行检查** —— 2 秒内应该出现：

```
[1s] blk 25/.. q1 0/8 q2 1/4 idle 5 latmax 14 parsemax 801 | L 24902B/s
     pkt ... inv 0 nr ... sync 1 slip 0 err 0 | heap 26488 min 26488 | stk 1256/768
```

如果看到 `blk 0` 而且 `idle` 在涨，说明雷达没在发数据 —— 查供电和 USART3。

## 1. 演示步骤

### 第 1 步 —— 一句话交代背景（15 秒）

> "Block 3.5 是在 `while(1)` 里轮询标志位来读雷达的。这次 Coding Day 把同一条数据通路
> 搬到 FreeRTOS 上，于是「中断上下文 ↔ 任务上下文」的交接变成显式的：DMA 填缓冲区，
> 中断只负责宣告哪一半就绪，一个任务负责解析，另一个任务负责呈现。"

然后指着串口输出说：

> "每块一个 12 字节描述符，每秒 25 块，解析任务从来没有落后过。"

### 第 2 步 —— 展示流水线在跑（60 秒）

让终端滚一下，按这个顺序指：

1. `#0474 p205 ok151 nr54 iv0 n115 d[47..10574] lat12 p765 S ...`
   > "每一行是一个 DMA 块：解出 205 个包、151 个有效、54 个无回波、0 个帧错误。
   > `n115` 是这个块碰到的不重复角度格数。`lat12` 是从中断到解析任务跑起来 12 微秒。"
2. `[1s] blk 25/472 q1 0/8 ...`
   > "每秒 25 块。**`q1 0/8`** 是关键 —— Queue 1 的峰值占用是 0，意思是解析任务总能在
   > DMA 卷回之前把队列排空。这就是 1024 字节块大小的实测依据。"
3. `L 24902B/s` 和 `pkt 96662`
   > "24.9 kB/s，约每秒 5 100 个包。和 C1 手册的约 5 000 点/s 对得上，说明没有丢数据。"
4. `inv 0 slip 0 err 0 sync 1`
   > "帧错误 0、重同步 0、串口错误 0，SCAN 响应描述符在启动时抓到一次。一个 5 字节包
   > 可能横跨两个 DMA 块，这三个计数器证明跨块状态机是对的。"
5. `heap 26488 min 26488 | stk 1256/768`
   > "32 KB 里用了 6.2 KB，而且剩余等于历史最低剩余，说明没有泄漏。解析任务还剩 1256
   > 字节栈，输出任务还剩 768。"

### 第 3 步 —— 证明它真的是 RTOS 驱动，不是轮询（45 秒）

这一步现场做，只要 10 秒：

1. **用手挡住雷达 / 指向墙面**
   - `d[..]` 的最小/最大距离变、`n` 变、`S` 扇区摘要变。
   - `blk` 还是 25、`q1` 还是 0 → 流水线依旧健康，只是数据变了。
2. **让传感器彻底停下**（拔掉雷达）
   - **拔哪根**：拔**雷达自己那根** 4/5 芯排线，在**雷达那一端**捏塑料接头拔（别拽线）。
     不要**拔 ST-Link 的 USB 线 —— 那是 COM8 和烧录口**；也不要**关小车总电源** ——
     那样 MCU 一起断电，串口也就没了。
   - `blk` 掉到 0，`idle` 开始涨，`cmd` 开始涨（看门狗在重发 SCAN），`sync` 复位，
     `err` 可能跳一次。
   - **系统不会卡死。** 两个任务依旧响应，1 Hz 行继续打印。
   > "这正是那种会让幼稚的 `osWaitForever` 设计死锁的故障场景。解析任务带 100 ms 保护
   > 超时；一旦**超过 1 s 没有 DMA 块到达**，就丢掉流锁定并每秒重发一次 SCAN 命令 ——
   > 你能看到 `cmd` 在往上跳。C1 上电后不会自己开始输出，没有这个机制它会永远静默。
   > 插回去 1-2 秒就恢复了。"

然后插回去，展示 `blk` 回到约 25、`idle` 不再增长、`cmd` 重新停住。
**这个自恢复过程是你现场最能说服人的东西。**

### 第 4 步 —— 在屏幕上指三层分离（30 秒）

> "三层，三个地方可以看：
> - **中断层** —— `lidar.c` 里的 `lidar_on_half()` / `lidar_on_full()`：只填一个 12 字节
>   描述符并投递，完全不解析。
> - **解析层** —— `app_rtos.c` 里的 `parser_task()` 调用 `lidar_parser_process()`，它用
>   队列里给的偏移量**直接从 DMA 缓冲区里读块**。
> - **呈现层** —— `output_task()` 只负责格式化和发送。
>
> 雷达的原始字节从来没有被拷进队列，进队列的只有偏移和长度。这就是为什么 Queue 1 传的是
> 12 字节而不是 1024 字节。"

## 3. 问答速查

题目要求必须能答的 8 个问题，配一句短答和支撑它的数字/文件。

| 问题 | 这样回答 |
|---|---|
| DMA 怎么一半一半填缓冲区？ | "一个 2048 字节循环缓冲，DMA1_Stream1 工作在 circular 模式。半满中断表示前半满，全满中断表示后半满。解析任务只读 DMA **没在写**的那一半，所以不需要锁。" |
| 半满/全满事件怎么标识一个就绪块？ | "`HAL_UART_RxHalfCpltCallback` → `lidar_on_half()` → 偏移 0；`HAL_UART_RxCpltCallback` → `lidar_on_full()` → 偏移 1024。各自投递一个带该偏移的描述符。" |
| ISR 为什么必须短？ | "实测：含上下文切换的交接延迟 12–15 µs。如果让 ISR 解析，那就是实测每块 801 µs 的工作量、每秒 25 次，会作为不可抢占延迟加在 IMU 的 I2C 和 UART5 DMA 上。" |
| Queue 1 为什么只放小描述符？ | "这样 ISR 完全不用拷贝：12 字节而不是 1024 字节，降低约 85 倍。数据本来就在 DMA 缓冲区里，任务只需要 `offset`+`length`。队列本身占 96 字节而不是 8 KB。" |
| 两个任务怎么在 BLOCKED / READY / RUNNING 之间迁移？ | "解析任务：在 `osMessageQueueGet` 上 BLOCKED，中断里的 `portYIELD_FROM_ISR` 把它变 READY，RUN 完投递 Queue 2。输出任务：阻塞在 Queue 2，解析任务 put 后变 READY。解析任务 99.5% 以上时间都是 BLOCKED —— `q1_peak = 0` 就是证据。" |
| 为什么解析任务优先级要高于输出任务？ | "解析任务的截止时间由硬件定：DMA 40 ms 后就覆盖半缓冲。输出任务的截止时间是给人看的 100 ms 一帧。错过解析截止 = 数据损坏；错过输出截止 = 晚打一行字。" |
| 创建了哪些 FreeRTOS 内存对象？ | "2 个队列（8×12 B 和 4×44 B，约 1.2 KB）、2 个任务栈 1536/2048 B、2 个 TCB，加上 `configUSE_TIMERS` 强制产生的空闲任务和定时器守护任务。总共占 32 KB `heap_4` 堆中的 6.2 KB —— `heap 26488 min 26488` 证明它不增长。" |
| 为什么解析 32、输出 24？ | "`osPriorityAboveNormal` 对 `osPriorityNormal`，来自 CMSIS-RTOS v2 枚举。不是随手定的：差一级就够，因为解析任务从不等输出任务。" |

### TA 可能追问的

| 问题 | 回答 |
|---|---|
| 解析任务如果跟不上了会怎样？ | "Queue 1 会满（深度 8 = 320 ms 余量）。第 9 个描述符时 ISR 丢弃并累加 `q_full`；`block_id` 的跳变让丢块可见而不是静默损坏。实测峰值是 0，从没发生过。" |
| 360 格扫描图有竞争吗？ | "单写者（解析任务）、单读者（输出任务）。读者在 `taskENTER_CRITICAL()` 里拷贝，阻止内核在拷贝中途切回去。用互斥量只会引入优先级反转风险 —— 这里根本没有可阻塞的对象。" |
| 为什么不用信号量而用队列？ | "信号量不携带数据。解析任务需要知道**哪一半**就绪、序号是多少 —— 那是 12 字节的信息，所以队列才是正确的原语。" |
| 输出任务为什么也带超时？ | "雷达停了就没有结果，任务将永远不去服务 IMU、也不打印 1 Hz 行。超时让呈现侧独立于数据通路继续存活。" |
| HAL 时基为什么放 TIM7 不放 SysTick？ | "SysTick 归内核。TIM6 已经被 IMU 的 100 Hz 触发占用，所以 TIM7 是空闲的基本定时器。这也正是课件推荐的做法规。" |
| 最难的一个 bug 是什么？ | **答案要背熟 —— 这是你最好的机会。** "把 tick 搬到 TIM 上之后 HAL_GetTick() 完全停摆。FreeRTOS 的 ARM_CM4F 端口把 `uxCriticalNesting` 初始化成 `0xaaaaaaaa`，只在 `xPortStartScheduler()` 里清零，所以调度器启动前每次 `osThreadNew` 都会把 BASEPRI 永久留在 0x50。BASEPRI 屏蔽外设中断但不屏蔽内核异常，所以 SysTick 时基从来不在乎、TIM 时基直接死掉。修法：TIM7 优先级设 0，在系统调用上限之上，而这是安全的，因为它不调用任何 RTOS API。" |

## 4. 必须记住的数字（只记这四个）

如果什么都记不住，记住这四个 —— 它们就是完整的故事：

| 数字 | 含义 |
|---|---|
| **1024 B / 40 ms / 每秒 25 块** | 块策略 |
| **12 字节 vs 1024 字节** | 为什么 Queue 1 小、为什么 ISR 短 |

| **12 µs vs 801 µs** | 交接 vs 解析 —— 为什么切分位置是对的 |

## 5. 可选但很加分：实时点云窗口

`pc_app/main.py` 解调固件从 UART5（230400）发出的**二进制遥测**，并画出 360 格扫描。
它是「流水线真的产出了一张二维地图」的视觉证据，而不只是日志行。

启动方式（会弹出一个标题为 *CodingDay - RPLIDAR C1 + MPU6500* 的窗口）：

```
D:\嵌入式小车\CodingDay_F446RE\pc_app\run_viewer.cmd
```

默认用 **COM10**，也就是已配对的 **HC-04** 模块（MAC `0426040302F4`）的传出 SPP 端口。
如果 Windows 改了端口号，用 `run_viewer.cmd -l` 列出口；`run_viewer.cmd --sim`
可以用**完全不需要硬件**的合成数据跑起来 —— 排练时的兜底方案。

> **可能被问到的波特率问题。** 固件在 UART5 上以 230400 发送，但 Windows 不允许把
> 蓝牙 SPP 虚拟串口开到 115200 以上。那个数值对 SPP 只是名义值 —— 真正干活的是射频
> 链路 —— 所以查看器用 115200 打开，什么都不会被限速。实测吞吐约 6.4 kB/s，与固件的
> 约 8.7 帧/s 吻合。

运行起来之后值得指的地方：

| 屏幕上的东西 | 说这句 |
|---|---|
| 左侧二维散点 | 「一整圈 360°、1 cm 分辨率，是 PC 用解析任务产出的 720 字节距离数组重建出来的。」 |
| 右侧极坐标航向盘 | 「这是同一帧遥测里的 MPU-6500 偏航角 —— 雷达和 IMU 是一起送过来的。」 |
| `fps 8.7  frames …  crc_err 0` | 「PC 用 XOR 校验解每一帧，一次都没有丢弃。」 |
| `LiDAR … B/s  pkt …  inv …  max … us` | 「这些和 COM8 上 `[1s]` 行的计数完全一致 —— 24.9 kB/s、0 无效、最坏解析 801 µs。两条独立通路互相印证。」 |
| 把手在传感器前晃 | 「环实时变形 —— 这就是 ISR → 队列 → 解析 → 队列 → 输出的完整链路。」 |

**如果窗口没弹出来**：确认小车已通电（HC-04 只有上电才会应答），并确认 COM10 仍然属于
HC-04。实在不行用 `--sim`，并说明 PC 解码器和固件共用同一套帧格式。

## 6. 演示中硬件挂了怎么办

1. 立刻说出来，不要闷头捣鼓。
2. 打开 `tools/logs/serial_*.txt` —— 之前的采集都带时间戳存在磁盘上。
3. 用日志里的同一批数字讲一遍，然后对着代码讲架构。
4. 兜底：`tools\flash_and_monitor.cmd -Probe` 一条命令就能区分「板子没电」和「固件卡死」——
   这本身就是一个不错的调试故事。

常见原因与一行检查：

| 现象 | 原因 | 检查 |
|---|---|---|
| `blk 0`、`idle` 在涨 | 雷达静默 | 雷达供电 / USART3 PC10-PC11 / SCAN 命令 |
| 终端什么都没有 | COM 口错 | `-Probe` 能连上目板；COM8 才是 ST-Link 虚拟串口 |
| 终端静默**且** `-Probe` 报 0.1 V | 板子没供电 | 主电源开关 |
| 复位后立刻卡死 | `configASSERT` / malloc / 栈溢出钩子 | 用调试器暂停，读 PC |
